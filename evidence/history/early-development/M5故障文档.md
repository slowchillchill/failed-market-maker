## Phase 11.8-G 诊断结论（2026-04-09 晚）

### G.1 评估结果

| 模型 | epoch | val_q | Trades | Flat ratio | Return mean |
|---|---|---|---|---|---|
| m5_run4b best | 5 | 0.0245 | 0 | 100.0% | 0.00% |
| m5_run4b final | 15 | 0.0366 | 5（全在 1 个 market） | 99.9% | 1.90%（单市场独角） |

- best_model 完全塌缩到 Hold
- final_model（过拟合）偶然在 1 个 market 上 market-buy down × 4，方向正确（label_up=false），+19.03%，但 335 其他 market 全 Hold
- D+E + Option 1（flip=0.5, zero_state=0.0, beta=3.0）**未解决** Hold 塌缩

### G.2 training_history 观察（run3/run4/run4b 三次对比）

| 指标 | run3 (50 ep) | run4 (15 ep) | run4b (15 ep) | 含义 |
|---|---|---|---|---|
| policy_loss | 4.29 → 4.20 | 4.65 → 4.68 | 4.69 → 4.69 | **冻结**，AWR 从未拉动 policy |
| q_loss | 0.058 → 0.046 | 0.040 → 0.038 | 0.041 → 0.038 | 正常下降 |
| v_mean | -0.41 → -1.60 | -0.21 → -0.98 | -0.13 → -0.91 | V 持续负漂 |
| reward_mean | 常数 -0.006 | 常数 -0.006 | 常数 -0.006 | 数据集静态均值 |

关键现象：policy_loss 三次 run 全都不动。AWR `exp((Q-V)/β)` 在这套数据上给所有动作的权重几乎相等，policy 头没有梯度方向可学。

### G.3 tick_stream 数据统计（v3.parquet，1.42M rows，1185 episodes）

**动作分布（决策层，不是成交层）**：
- Hold 58.5%, OpenUp 9.3%, OpenDown 8.8%, Reduce 7.9%, Close 7.3%, Flip 9.4%
- 动作分布本身是平衡的，**不是数据缺少非 Hold 样本**

**`has_trade=True` 的 1.07% 行的 reward**（按动作）：
| 动作 | n | mean reward | n_pos | n_neg | 胜率 |
|---|---|---|---|---|---|
| OpenUp | 4268 | **-0.25** | 176 | 4092 | 4.1% |
| OpenDown | 3817 | **-0.24** | 186 | 3631 | 4.9% |
| Close | 2868 | +0.023 | 811 | 2057 | 28.3% |
| Flip | 3035 | +0.002 | 768 | 2267 | 25.3% |
| Reduce | 697 | -0.067 | 125 | 572 | 17.9% |

**每 episode 聚合（(window, market) 对，n=1185）**：
- NAV delta：mean **-1.35%**, median -1.12%, 71.1% 亏损 / 28.9% 盈利
- reward sum：mean -6.49, 92.7% 负、7.3% 正
- 采集策略（pretrained M3 + softmax 探索）**整体是净亏损的**

**赢家 vs 输家 episode 动作分布**：
- 赢家 (n=342, 平均 +4.9%)：**87% Hold** + 13% 交易
- 输家 (n=843, 平均 -3.9%)：**44% Hold** + 56% 交易
- 即：**交易越多，越亏钱**

### G.4 根因判定

**IQL/AWR 的行为完全正确。** 在数据层面：
1. 采集策略的"交易行为"是净亏损
2. Hold 在数据中是 locally 最优选择
3. Q 函数正确学到 Q(s, Hold) ≥ Q(s, OpenUp/Down/...)
4. Policy 正确提取"全 Hold"
5. policy_loss 冻结因为 AWR weights 在所有动作上几乎均匀

**这不是训练 bug，不是模型架构 bug，不是探索多样性不足。** 是**数据质量问题**——采集策略本身不会交易赚钱。IQL 只能做 offline improvement 到"**不比采集策略差**"，而采集策略的下界是 Hold，所以 IQL 收敛到 Hold。

### G.5 可选后续方向

1. **改采集策略（Option X）**：pretrained + softmax 不够好
   - 加门限：只有 signal head 置信度高时才交易
   - 多策略混合：规则、动量、基线启发式
   - 带终态 leak 的 oracle 采集（synthetic winners）
2. **Filtered BC（Option Z）**：只在赢家 episode 上做 behavior cloning
   - 直接模仿 87% Hold + 稀疏高置信度交易模式
   - 简单、可解释、几乎肯定有效
3. **重新设计 reward**（Option Y）：
   - 稀疏化——只在 settlement 时给一次终态 reward
   - 对称放大盈利、缩小小额亏损
4. **放弃 offline RL，改在线或半在线训练**（RLHF 风格）

**我的推荐**：先做 **Filtered BC** ——工程量最小，可以验证"数据里是否真有可学的策略"。如果 Filtered BC 能做到 >50% Hold + 稀疏正确交易，说明 IQL 超参调优才有意义；如果连 Filtered BC 都塌缩到 Hold，就需要动 Option X 或 Option Y。

## 3. 故障症状

### 3.1 表面现象

运行任何形式的 `agent evaluate` 都在同一点卡住：

```
[evaluate] split=test windows=10 model=... output=...
[evaluate] strategy=agent threshold=0.55 force_order_type=None fixed_size=None
<hang forever>
```

- 进程不消耗 CPU（`utime≈0, stime≈0`）
- 只有 1 个线程（正常情况下 ORT 会起线程池）
- RSS 约 5 MB（ORT session 未创建时的 Rust 二进制基线）
- `wchan = futex_wait_queue_me`
- 进程内存映射里只有 `ld-linux / libc / libgcc_s`，**没有任何 ORT / CUDA 相关库被加载**
- `nvidia-smi` 显示 0 MiB GPU 内存、0 W 功耗

### 3.2 卡死位置定位

用 `stdbuf -oL` 对 `agent run --model-path /nonexistent.onnx` 的测试确认：

```
[agent] Model: /nonexistent.onnx
[agent] seq_len: 240
[agent] step_ms: 250
[agent] size_mapping: [5.0, 15.0, 30.0]
<hang>
```

- 卡死点在 `main.rs:285` 的 `AgentStrategy::new(agent_config)?`
- 即使模型路径完全不存在也卡死，说明**不是 ONNX 文件本身的问题**
- 卡死发生在 `OnnxInference::load()` → `Session::builder().commit_from_file(...)` 内部，在真正打开文件之前

### 3.3 已排除的可能

| 假设 | 验证方式 | 结论 |
|------|---------|------|
| 模型 ONNX 损坏 | 用 `run3` 的已知好 ONNX | 同样卡死 |
| 本地 eval dir 冲突 | 输出改到 `/tmp` | 同样卡死 |
| 并行跑两个 eval 的锁竞争 | 串行单个跑 | 同样卡死 |
| 残留 agent 进程占 GPU | `pkill -9` + `nvidia-smi` 确认干净 | 同样卡死 |
| 训练残留 CUDA 上下文 | **重启服务器** | 同样卡死 |
| CUDA EP 初始化挂起 | 改 `init_ort_environment()` 去掉 `CUDA::default()`，重编译 | 同样卡死 |
| `agent` 二进制损坏 | `agent --help`, `agent run --help` | 正常返回 |
| `replay-engine` 能用（无 ORT） | `replay-engine --help` | 正常 |
| PyTorch CUDA 坏掉 | `torch.zeros(1).cuda()` | 正常 |
| 缺少 CUDA 运行时库 | `ldconfig -p \| grep libcudart/libcudnn` | 都能找到 |
| 系统负载/资源限制 | `uptime`、`ulimit -a` | 负载 4.25 / 25 核，无限制 |
| `onnx-inference` crate 的 `load_and_run_inference` 测试 | `cargo test --ignored` | 同样卡死 |
