### Phase 2：feature-engine crate

新建 `poly-arb-ai/rust/feature-engine/`，Cargo workspace 同步新增成员。

#### 特征帧（79 列）

特征帧结构体 `FeatureFrame`（`frame.rs`）：

| 分组 | 列数 | 说明 |
|---|---:|---|
| 索引 | 7 | dataset_version / window_id / market_id / decision_ts_ms / time_to_expiry_ms / step_index / cold_start |
| Polymarket Up | 18 | 最优价 / spread / mid / 盘口失衡 / last_trade_price / last_trade_size / last_trade_is_buy / 各 5 档深度 |
| Polymarket Down | 18 | 同上，Down 侧 |
| Binance 原始 | 7 | 最优价 / spread / mid / last_price / last_is_buyer_maker / last_size |
| Binance 衍生 | 3 | **market_drift**（market 内累计漂移）/ trade_imbalance / volatility（后两者来自 60s 滚动窗口） |
| Binance 深度 | 10 | bid/ask_qty_[1-5] |
| BLB | 3 | bps / level_count / barrier_usdt |
| Chainlink | 4 | value / p2b_deviation / staleness_ms / short_term_change |
| Agent 状态 | 6 | cash / up_shares / down_shares / nav / position_value / **floating_pnl** |
| 标签 | 3 | y_cls / y_ev_up / y_ev_down |

`poly_*_last_trade_is_buy`：1 = taker 买入（hit ask），0 = taker 卖出（hit bid），null = 原始事件无 side 字段。

#### 因果性保证

`FeatureCollector`（`collector.rs`）中的 catch-up 帧问题：当时钟以大步长跨越多个 step_ms 边界时，中间帧本不应看到触发该大步的事件数据。

解决方案：在每次 `on_step` 末尾保存 `prev_prototype`（轻量字段快照，不含盘口所有权）。边界 `< now_ms` 的 catch-up 帧使用 `prev_prototype`；边界 `== now_ms` 的帧才使用当前状态。

#### y_ev 精确口径

y_ev 不能用 `t_decision` 时刻盘口近似——目标市场（BTC 二元期权）在 20ms 内盘口变化极大，误差不可接受。

解决方案：pending_yev 队列 + `prev_polymarket` 快照。帧发出时 y_ev = None；同时入队 `(frame_idx, t_decision + 2 × polymarket_visible_delay_ms)`。当 `on_step` 推进到 `now_ms >= target_ts` 时回填：
- `now_ms == target_ts`：精确命中，用当前盘口
- `now_ms > target_ts`：用 `prev_polymarket`（上一事件后的快照），避免被触发此 `on_step` 的更晚事件污染

market 结束时，`take_all_frames()` 用 `prev_polymarket` 强制回填所有未兑现的 pending 项，消除市场末尾的覆盖缺口。

这实现了 PRD 要求的 `y_ev 按 t_exchange_arrival 时刻真实盘口回填`。

#### BLB 指标

`blb.rs` 计算三个指标：
- `bps`：`(current_price - binance_p2b) / binance_p2b × 10000`（`binance_p2b` 取该 market 第一条可见 Binance aggtrade 价格）
- `level_count`：mid 与 p2b 之间的 Binance 档位数（正负符号表示方向）
- `barrier_usdt`：对应档位的 `∑(price × qty)`（同符号）

#### 输出格式

Snappy 压缩 Parquet，含 Arrow 可空类型（`Option<f64>` → Float64 nullable，`Option<bool>` → Int8 nullable）。

#### CLI

```bash
cargo run --release --manifest-path poly-arb-ai/rust/Cargo.toml -p feature-engine -- \
  --dataset-version data-v1 \
  [--window-id <id>] \
```

## 本次开发时遇到的问题

### 1. 因果性泄漏（catch-up 帧）

最初实现中，catch-up 帧直接读取当前事件触发后的状态——这是未来泄漏：一个 250ms 边界帧在 500ms 时刻被发出，如果使用 500ms 时刻的盘口，就把 251ms-500ms 期间的所有事件信息写入了 250ms 的特征帧。

解决：`prev_prototype` 快照方案，每次 `on_step` 结束时保存上一步的完整特征字段。catch-up 帧使用 `prev_prototype`，边界恰好等于 `now_ms` 时才用当前状态。

### 2. y_ev 近似的不可接受误差

初版评估认为 t_decision 盘口作为 y_ev 的近似"影响有限"（20ms 延迟）。用户指出这一判断是错误的：目标市场是 BTC 二元期权，在重要消息时 20ms 内盘口会发生剧烈变化，用 t_decision 盘口会系统性高估 y_ev（因为此时买 Up 仍然便宜，但在真实成交时盘口已大幅移动）。

解决：pending_yev 队列，精确使用 `t_decision + 2 × delay` 时刻的盘口计算 y_ev。

### 3. Arrow meta-crate 不在 lockfile

`Cargo.toml` 中 `arrow = "56"` 会触发依赖解析失败（meta-crate 缺少稳定路径）。改为直接引用子 crate `arrow-array = "56.2"` 和 `arrow-schema = "56.2"`。

### 4. MarketDescriptor 字段名与 AccountState 方法签名

编译期发现多处签名不匹配：
- `MarketDescriptor::start_ts_s`（秒）需乘以 1000 转毫秒
- `AccountState::shares` 需传 `(&str, Outcome)` 两参数（含 market_id）
- `AccountState::nav` 需传 `&ActiveMarketState`（不是分别传 polymarket + chainlink）

均在编译错误提示后直接修正。

### 5. Python 包目录名含连字符

`poly-arb-ai` 含连字符，Python 无法作为包直接导入。采用 `PYTHONPATH=poly-arb-ai` + `from training.dataloader import FeatureDataset` 绕过，保持目录名不变。

### 6. 技术审查修复（第二轮）

第一版实现完成后，经技术审查发现并修复以下 5 个问题：

- **`y_ev` 被触发事件污染**：`on_step` 在事件应用后调用，`now_ms > target_ts` 时用的是包含当前事件的盘口。修复：新增 `prev_polymarket` 字段，在 `now_ms > target_ts` 时用上一事件结束后的状态，仅 `now_ms == target_ts` 时用当前状态。
- **`window_id` 恒为 "all"**：构造器参数被写死传入，未从 `MarketDescriptor.window_id` 读取。修复：`reset_for_market()` 中改为 `self.window_id = market.window_id.clone()`，构造器移除该参数。
- **y_ev 末尾 market 覆盖缺口**：market 转换 flush 只覆盖第 1…N-1 个 market，最后一个 market 的 pending_yev 在 `take_all_frames()` 时被遗漏。修复：`take_all_frames()` 中增加用 `prev_polymarket` 兜底 flush。
- **`agent_floating_pnl` 定义错误**：原实现中用 `agent_position_value` 代替浮盈亏（两者不等，position_value 包含成本）。修复：在 `AccountState` 新增 `cost_basis: HashMap<String, f64>`，买入时累积；`floating_pnl = position_value - cost_basis`。
- **`binance_mid_return` 语义错误**：该列实为 market 起始价格的累计漂移（非滚动 return）。修复：全局重命名为 `binance_market_drift`，注释同步更新。

### 7. 技术审查修复（第三轮）

- **Python 测试自包含**：`test_dataloader.py` 改为使用 `synthetic_parquet` fixture（`conftest.py` 自动生成含正确 79 列 schema 的合成 Parquet，三个 fake market），无需 Rust 二进制或外部文件即可运行全部 13 个核心测试。同步修复 `conftest.py` 中 `FEATURE_COLS` 与 `_INDEX_COLS` 重叠（`time_to_expiry_ms` / `step_index` 同时存在两处）导致 Arrow schema 重复字段名、`schema.field()` 报 KeyError 的问题；修复方式：构建 schema 时跳过已在 `_INDEX_COLS` 的 FEATURE_COLS 字段，构建 arrays 时对列名去重。
- **BLB depth 视图对称性**：`collector.rs` 中 `blb_bids` / `blb_asks` 改用 `.take(fill_k)` 而非全量 `bin_bids` / `bin_asks`。当库调用方传 `top_k > 5` 时，BLB 看到的档位数与导出的深度列（`binance_bid/ask_qty_[1-5]`）一致，消除语义不对称——修复前 `blb_level_count` 可能引用深度列中不存在的第 6+ 档。
- **y_ev 定点测试**（`y_ev_penultimate_frame_always_filled`）：对每个 market 的倒数第二帧，分别断言 `y_ev_up`（proxy：`poly_up_best_ask` 非 None）和 `y_ev_down`（proxy：`poly_down_best_ask` 非 None）均已填充，Up/Down 独立检查。比 `y_ev_coverage_acceptable` 更严格：针对结构不变量而非统计速率，单个违例即失败。**局限**：仅证明 pending_yev queue 在 non-terminal 帧上按时 fire；不证明使用的是精确 `t_exchange_arrival = t_decision + 2×delay` 快照（证明精确快照需要可控合成 replay，不在本轮范围）。

## 与原计划不一致的地方

### 1. y_ev 精度需求触发了额外的 pending_yev 队列设计

计划文档最初描述 y_ev 使用 `t_decision` 时刻盘口，属于已知近似。实际评审后确认该近似对 BTC 二元期权不可接受，因此额外引入了 pending_yev 队列机制（约 50 行额外代码，但设计干净，不影响其他部分）。

### 2. 增加了 7 个衍生特征列（相比原计划）

相比原计划，额外增加了：`binance_market_drift`、`binance_trade_imbalance`、`binance_volatility`、`chainlink_short_term_change`、`agent_position_value`、`agent_floating_pnl`、以及原计划未完整说明但已实现的 `poly_*_last_trade_size`/`poly_*_last_trade_is_buy`（Up/Down 各 2 列）。这些都是从已有状态直接派生的低成本特征，增量价值明确。

### 8. 技术审查修复（第四轮）：data-v3 覆盖缺口 + per-market 错误恢复

数据集输出审查发现 data-v3 有严重覆盖缺口：manifest+labels 期望 1188 个有效 market，实际 parquet 仅含 1115 个，缺失 73 个。根因是 feature-engine 的错误处理粒度为**窗口级**（`run_with_strategy` 任意 market 出错 → 整窗口所有帧丢弃），而 3 个窗口内各有 1 个 NDJSON 截断文件，导致每窗口剩余 30+ 个正常 market 一并丢失。

修复内容：

- **`replay-engine/src/replay.rs`**：`StrategyCallback` 新增两个生命周期 hook（默认 no-op）：
  - `before_market(&mut self, market: &MarketDescriptor)`：market 事件循环开始前调用，供实现方记录回滚检查点
  - `discard_market(&mut self)`：market 出错时调用，供实现方丢弃本 market 已累积的部分状态
  - `run_with_impl` 的 market 循环改为 per-market 错误处理：将 `PolymarketSource::load` 至最终 `process_scheduled_events` 的全部代码包在闭包内；出错时：① drain 共享数据源（aggtrades/orderbook/chainlink）至该 market 的 `end_ts_ms`，防止游标污染后续 market；② 调用 `strategy.discard_market()`；③ `continue` 跳过 settlement 和 report 更新
- **`feature-engine/src/collector.rs`**：`FeatureCollector` 新增 `frames_at_market_start: usize` 字段；实现 `before_market`（记录 `all_frames.len()`）和 `discard_market`（截断 `all_frames` 至检查点、清理引用已丢弃帧的 `pending_yev` 条目、重置 per-market 状态字段）

修复效果：data-v3 从 1115 market / 1,336,404 帧 → **1185 market / 1,420,307 帧**，覆盖率从 93.9% 提升至 **99.7%**。

**已知遗留问题（不可恢复）**：data-v3 三个窗口各有 1 个 NDJSON 截断文件，对应 3 个 market 无法导出：
- `1774713600-1774728000`：截断 1 个 market
- `1774872000-1774886400`：截断文件 `btc-updown-5m-1774883400.ndjson`（EOF at col 141），截断 1 个 market
- `1775260800-1775275200`：截断 1 个 market

这 3 个 market 属于原始数据损坏，修复需重新采集对应原始文件，当前不处理。

## 追加记录（2026-04-24）：typed parquet 原始镜像层当前交接口径

上面的 parquet 记录保留的是 `data-v1` 单窗口验证；当前面向交接的正式口径补充如下：

- `feature-engine` 对 mirror 的支持不是单独再实现一套读取逻辑，而是通过 `ReplayEngine::run_with_strategy` 自动继承 `model/parquet-data/<dataset_version>/` 下的 typed parquet 原始镜像层输入能力。

- 当前最新完成的全量 mirror 校验是 `data-v4` 的 source-layer coverage：`3016 -> 3016`，且 `missing/extra/row_mismatch` 全为 `0`。
- 这意味着 `data-v4` 的 mirror 在**文件覆盖与逐文件行数**层面已经通过校验，但不应把它写成“`feature-engine` 已对 `data-v4` 全窗口完成 raw/parquet 全量特征等价验证”。
- 本日志里后续出现的 `v1/v2/v3` 全量帧数，仍应理解为历史 raw 基线或阶段性导出结论；当前 mirror 侧的正式强验证范围仍以 `data-v1` 样本对拍和 `data-v4` coverage 校验为准。
