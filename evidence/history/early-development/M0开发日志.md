## 本次开发反馈

### 1. 可观测性必须内建

- 数据任务运行时间长，终端如果长时间无输出，容易被误判为卡死。
- 后续凡是长时间扫描、下载、导出、校验的数据任务，都应默认打印阶段日志和进度条。

### 2. `data-v3` 的增量更新不是四路原始数据天然齐全

- 实际工作流里，`data-v3` 会先同步 `btc-updown-5m/`、`btcusdt-orderbook/`、`rtds_chainlink/`。
- `btcusdt-price/` 需要额外调用 Binance aggTrades API 回填，因此必须把“发现缺口 -> 批量回填 -> 重跑 validate/export”纳入正式流程。

### 3. orderbook 产物范围应控制在 M0 所需最小闭环

- 当前确认的 M0 范围是：
- 保留 `orderbook_index.parquet`
- 新增 `orderbook_summary.parquet`
- 暂不生成全量 `price-level parquet`

这样既能满足回放和数据检查，又不会在 M0 过早引入高体积、低复用的盘口价位明细表。

### 4. 跨版本原始数据的异构性比计划中更强

- `data-v2`、`data-v3` 会同时出现 finalized 文件与 `*-running.*` 文件。
- 同一窗口下可能存在多个分片文件，而不是单文件。
- 个别 `running` 文件含坏 JSON 行，不能因为单行损坏让整批任务中断。

因此，数据发现与解析逻辑必须以“容错优先”为原则，而不是假设原始目录始终严格整洁。

### 5. M0 阶段已经出现少量“便捷摘要列”

- `polymarket_events.parquet` 中包含 `bid_level_count`、`ask_level_count`、`top_5_bid_qty`、`top_5_ask_qty`。
- 它们是从单条 `book` 事件直接汇总出的规范化辅助列，不是 M2 才会构造的跨源特征。
- 这类字段可以保留，但文档里必须明确边界，避免与后续特征工程混淆。

## 与原计划不一致的地方

### 1. `manifest.parquet` 目前未直接包含 `p2b` 与 `resolution`

原计划在 M0.1 中写的是：

- `market_id / start_ts / end_ts / p2b / resolution`

当前实现中：

- `manifest.parquet` 主要承载窗口索引、路径索引和有效性状态
- `p2b` 与 `resolution_price` 被放在 `labels.parquet`

这意味着下游如果只读取 `manifest.parquet`，还需要额外关联 `labels.parquet` 才能拿到完整标签信息。这是目前最明确的一处实现偏差。

### 2. M0 判定标准中的“288 markets 全部通过”不符合真实数据状态

原计划总览把 M0 判定标准写成：

- `288 markets 全部通过对齐验证`

但实际接入 `data-v1`、`data-v2`、`data-v3` 后发现，原始数据天然存在 gap、缺失标签、缺失源文件等问题，不可能把“全部通过”作为真实验收口径。当前更合理的落地标准是：

- 能稳定生成训练层 parquet
- 能输出每个数据版本的通过/丢弃统计
- 能保留明确的 `drop_reason`

### 3. 计划文档没有预留 `btcusdt-price` 回填这一实际步骤

原计划默认四类原始数据都已在本地可用，但今天的实际开发表明：

- `data-v3` 的日常更新流程里，`btcusdt-price/` 需要单独回填
- 因此 M0 实际多了一个“数据缺口修复工具链”，即单窗口抓取器 + 批量回填器

### 4. 计划文档未明确 orderbook 在 M0 的最终导出边界

今天的实现已确认：

- M0 保留 `orderbook_index.parquet`
- M0 新增 `orderbook_summary.parquet`
- M0 不导出全量 `price-level parquet`

这属于实施过程中确认下来的范围收敛，建议视为 M0 的正式口径。

### 5. `condition_id` 当前与 `market_id` 采用同一来源

当前实现里，`condition_id` 从 Polymarket 原始事件的 `market` 字段读取，并同时作为本管线的 `market_id` 主键使用。计划文档没有写明这一点，因此文档层面容易让人误以为二者已经被严格区分；实际上目前仍是“同源同值，保留未来拆分空间”的状态。

## 后续建议

- 如果要严格对齐 M0.1 文案，应继续补齐 `manifest.parquet` 中的 `p2b` / `resolution_price`。
- 如果决定维持当前 schema 拆分，则应把计划文档与 README 的口径同步改成“manifest + labels 联合提供标签信息”。
- 后续每次 `data-v3` 增量同步后，建议固定执行：`dry-run backfill -> backfill -> validate -> export`。

## 追加记录（2026-04-24）：typed parquet 原始镜像层当前口径

为避免交接时把上面的 `data-v1` 追加记录误读成“一次性样本实验”，当前正式口径补充如下：

- `model/parquet-data/<dataset_version>/` 是 raw 原始事实层的**同构镜像目录**，不是新的训练层表；`data-pipeline` 已可通过 `--raw-root` 直接把它当作 `M0` 输入。
- 当前最强的 `M0` 等价性结论仍来自 `data-v1` 样本：文件覆盖、逐源行数、单窗口 `manifest / labels / validation` 等价均已验证通过。
- 当前最新完成的全量 mirror 校验是 `data-v4`：`verify_parquet_raw_coverage.py` 结果为 `3016 -> 3016`，且 `missing/extra/row_mismatch` 全为 `0`。
- 上述 `data-v4` 结果当前只证明**文件覆盖与逐文件行数一致**；它不应被表述成“所有版本、全链路、全窗口都已完全等价”。
- `M0` 的正式下游契约仍是 `manifest.parquet + labels.parquet` 联合消费；mirror 只改变原始事实层的存储/读取形态，不改变这个索引与标签接口。
