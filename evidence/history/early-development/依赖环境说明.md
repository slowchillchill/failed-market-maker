## 3. M0 -> M1 的调用关系

M1 不是直接自己重新扫描 `model/data-*`，而是先消费 M0 的训练层索引，再沿索引回到原始数据。

调用顺序：

1. 读取 `poly-arb-ai/data-pipeline/out/<dataset_version>/manifest.parquet`
2. 读取 `poly-arb-ai/data-pipeline/out/<dataset_version>/labels.parquet`
3. 以 `dataset_version / window_id / market_id` 关联 manifest 与 labels
4. 只选 `is_valid = true` 且 `label_status = valid` 的 market
5. 再使用 `manifest` 中的 `poly_path / aggtrades_path / orderbook_path / chainlink_path` 回到原始数据流

这意味着：

- `manifest.parquet` 不能单独作为完整标签输入使用
- 当前必须 `manifest + labels` 联合消费

## 4. 重要数据约定

- `market_id` 与 `condition_id` 当前同源同值，均来自 Polymarket 原始事件的 `market` 字段
- `manifest.parquet` 当前不直接包含 `p2b / resolution_price`；它们在 `labels.parquet`
- `tables/*.parquet` 只包含通过验证的 market
- `manifest.parquet`、`labels.parquet`、`validation.parquet` 包含所有发现到的 market
- 路径字段是绝对路径
- 当路径指向目录而不是文件时，表示该源存在多分片；读取时按文件名顺序拼接为一个逻辑流
- 原始 JSON Lines 读取规则是 finalized 文件优先，必要时回退到 `*-running.*`
- 新数据集版本沿用相同主键：`dataset_version / window_id / market_id`
- 下游不能只读取 `manifest.parquet`；必须联合消费 `manifest + labels`

## 7. 当前已知偏差与注意事项

- M0 文案里要求 manifest 直接包含 `p2b / resolution`，但当前实现采用 `manifest + labels` 拆分
- Rust 工程已迁入 `poly-arb-ai/rust/`，避免仓库根被 Rust workspace 占用，并为后续 `feature-engine`、`evaluator` 等 crate 预留结构
- 当前存在项目级规则 `.cursor/rules/data-test-progress-visibility.mdc`：数据任务与测试任务必须在终端持续输出进度
- 长窗口回放即使在高配机器上也可能偏慢，因为当前实现是单线程事件驱动，主要瓶颈在大规模 JSON/CSV 解析与逐事件状态推进；完整验收优先使用 `--release`
- 全量扫描 `data-v1 / data-v2 / data-v3` 后，当前确认共有 `249` 个唯一 market 缺少 `market_resolved`，其中 `data-v1=6`、`data-v2=13`、`data-v3=230`
- 上述 `249` 个 market 已全部写入本地覆盖表；最近一次复扫结果为 `override_missing_market_count = 0`
- 后续 `data-v3` 增量更新后，必须重新执行扫描脚本确认是否出现新的缺口；优先使用 repo 内 `--fetch-missing-from-gamma`，如果环境无公网再退回外部拉取 + `--merge-file`
- M1 当前已具备 limit/maker 最小闭环，但仍属于事件驱动单策略骨架，后续策略与成交模型仍可继续扩展
- M2 的**历史初版** feature-engine 输出是 **79 列**；当前仓库在 `M5 S1` 后的 **canonical schema** 已扩展为 **86 列**。`FEATURE_COLS` 仍是 **65**（63 纯特征列 + `time_to_expiry_ms` / `step_index` 来自索引列）；`M5/M6` 的观察输入则是 `76` 维（`65 + 6 agent state + 5 long-term signal`）。y_ev nan（3–5%）为 market 末尾流动性枯竭导致，非覆盖缺口
- feature-engine 全量产出：v1=294,834 帧 / v2=894,106 帧 / **v3=1,420,307 帧**（99.7% 覆盖率，3 个 market 因原始 NDJSON 截断无法恢复）
- feature-engine 输出目录约定：`poly-arb-ai/rust/feature-engine/out/<dataset_version>/features_<step_ms>ms.parquet`
- **`StrategyCallback` 接口变更**（M3 及后续实现自定义策略时需注意）：新增两个带默认 no-op 实现的 hook——`before_market(&mut self, market: &MarketDescriptor)` 和 `discard_market(&mut self)`；自定义实现若需 per-market 回滚能力（如 FeatureCollector），应重写这两个方法；不重写则行为与之前完全一致
- **M3 InputNormalizer 契约**：训练前须调用 `model.normalizer.set_stats(mean, std)`；`feature_stats.npz` / `feature_stats_76.npz` 是训练 → 导出 → 追溯链路上的配套工件，必须与导出的模型成套保存。当前 Rust ONNX runtime 不直接读取该文件，因为 normalizer 已烘入 ONNX 图；但若训练统计与导出模型混用，仍会造成 silent drift
- **M3 NaN 处理**：model.py 使用 `torch.where(normed!=normed, zeros, normed)` 处理 NaN（IEEE 754 特性），避免 `nan_to_num` 的兼容性问题
- **M3 batch_size 对 GPU 利用率的决定性影响**：RTX 5090 + batch=128 → GPU 仅 10%，VRAM 仅 1.1GB/32GB；batch=2048 → GPU 92%，VRAM 7-9GB；batch 是影响 GPU 效率的首要因素，须根据 VRAM 尽量放大
- **M3 AMP bfloat16 eval bug**（已修复）：开启 `--amp` 时，eval_epoch 中模型输出为 bfloat16，直接 `.cpu().numpy()` 报 `TypeError: Got unsupported ScalarType BFloat16`；修复：在 `.numpy()` 前加 `.float()`
- **M3 跨数据集时间泄漏**（Run 1/2，已修复）：各 parquet 独立 time_ordered_split + ConcatDataset 导致训练集包含比 val/test 晚 10.6 天的数据；修复：FeatureDataset 支持多路径合并，train.py 改为全局时间排序后统一切分
- **M3 torch.compile checkpoint 兼容**（Run 1/2，已修复）：`model.state_dict()` 在 compile 包装后 key 带 `_orig_mod.` 前缀，无法直接加载到普通模型；修复：保存时用 `model._orig_mod.state_dict()`
- **M3 FeatureDataset 多路径支持**：`FeatureDataset` 的 `parquet_path` 参数现在接受 `str | list[str]`，多路径时自动用 `pyarrow.concat_tables` 合并后构建统一索引

- **M4 ort crate 版本**：`ort = "2.0.0-rc.12"`（pre-release），正式版 2.0 尚未发布。ort v2 API 与 v1 差异较大：`Session::builder()` 链式调用、`session.outputs()` 方法（非字段）、`outputs.get("name")` 按名称获取、`try_extract_tensor::<f32>()` 返回 `(&Shape, &[f32])` 元组
- **M4 StrategyCallback 扩展**：新增 `on_decision_tick()` 和 `schedule_next_tick()` 默认 no-op 方法。现有策略（AlwaysBuyUpMarket / FeatureCollector）无需修改。实现 `on_decision_tick` 的策略需在 `before_market` 中初始化 `next_tick_ms`
- **M4 OrderSide 向后兼容**：`OrderIntent.side` 为必填字段。现有 `AlwaysBuyUpMarket` 已更新为填 `OrderSide::Buy`
- **M4 AccountState.cost_basis 接口变更**：`cost_basis_for_market(market_id)` 已废弃，改用 `cost_basis_for_position(market_id, outcome)`（按 `(market_id, Outcome)` 存储）。`feature-engine` 中已同步更新
- **M4 SizeHead 语义**：SizeLevel = 目标仓位档位（5/15/30 shares），非增量。OpenUp+Small(5) 表示"设 Up 腿目标为 5 shares"，若当前持仓 20 则减仓
- **M4 ONNX 模型依赖**：Agent CLI 需要预先导出的 ONNX 模型。若 M3 checkpoint 更新，须重新运行 `export_onnx.py`
- **M4 新增 Python 依赖**：`onnx`、`onnxruntime`（用于 ONNX 导出验证，agent 回放不需要）
