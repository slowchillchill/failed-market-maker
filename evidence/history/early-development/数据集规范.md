# 数据集规范

> 适用于 `model/data-v*` 的新数据集版本创建与维护，当前重点面向 `DATA-V4`。
> 当旧文档与当前实现冲突时，以本文、`poly-arb-ai/dev-docs/依赖环境说明.md`、`poly-arb-ai/dev-docs/M5待解决问题.md` 的最新口径为准。

## 1. 目标与适用范围

本规范定义新数据集版本在当前项目状态下必须满足的目录结构、数据完整性、跨阶段接口和验证流程。它不是只为早期 `M0/M3` 服务，而是要直接兼容当前已经收口到 `M5`、正在准备 `M6` 的真实系统状态。

当前默认状态：

- `M0`-`M5` 已完成，当前进入 `M6`（Paper Trading）准备。
- `M6` 默认候选不是“完整 RL 收敛出的 6-class final policy”，而是：
  `frozen signal head + signal_threshold=0.58 + force_order_type=limit + 默认 size`
- 新数据集必须至少支持：
  - `M0` 的 `validate/export`
  - `M1/M2` 的真实回放与特征提取
  - `M3` 的严格时间前推监督训练
  - `M4/M6` 的 replay / evaluate / paper trading 验证
- 如果未来需要再做 `M5` 类离线诊断，新数据集也必须能产出可复核的 `tick_stream` 与 `reward_minimal` 口径数据，但这不再是 `DATA-V4` 的默认主线。

## 2. 原始目录结构

新数据集版本必须使用如下目录结构：

```text
model/
  data-v4/
    <window_id>/
      btc-updown-5m/
        btc-updown-5m-<market_start_ts>.ndjson
        ...
      btcusdt-orderbook/
        *.ndjson / *.nojson
      btcusdt-price/
        *_ms.csv 或 *.csv
      rtds_chainlink/
        *.ndjson / *.nojson
```

硬约束：

- `data-v4/` 下一级目录必须直接是 `<window_id>`，不能再额外套一层日期目录。
- `<window_id>` 必须是 `1774248000-1774334100` 这种 `首个 market 开始时刻-最后一个 market 开始时刻` 的形式。
- 当前 `data-pipeline` 的自动发现逻辑只扫描 `model/data-v*/<window_id>/` 这一层；旧文档中出现过的 `model/data-v1/20260325/1774248000-1774334100/` 示例，已经不再符合当前代码口径。
- `btc-updown-5m/` 下每个文件对应一个 5 分钟 market，文件名中的时间戳是该 market 的开始时刻。
- `btcusdt-orderbook/` 与 `rtds_chainlink/` 允许由多个分片文件组成；下游会按文件名顺序拼接为逻辑流。
- `btcusdt-price/` 在原始同步结束时可以暂时缺失，但在进入 `validate/export` 前应先补齐；缺失不应被长期视为“可接受常态”。

窗口与 market 计数约定：

- `window_id` 的两个时间戳都是 market 的开始时刻，不是结束时刻。
- market 数量公式固定为：
  `market_count = (last_start - first_start) / 300 + 1`

## 3. 原始数据完整性要求

每个 market 的有效性校验，固定围绕以下四类原始数据源展开：

1. `Polymarket btc-updown-5m orderbook`
2. `Binance BTCUSDT aggtrades`
3. `Binance BTCUSDT orderbook`
4. `Chainlink BTC/USD`（统一按 Polymarket 转发链路建模）

硬约束：

- 任一数据源在 market 内存在超过 `15s` 的缺口，该 market 必须判为无效。
- `BLB` 不是独立原始源，不需要单独文件；它由 `feature-engine` 基于 Binance 数据实时计算。
- `Chainlink` 同时承担标签源和特征源，但两者时间口径必须严格分离：
  - 标签口径：market 结束后的 `resolution_price`
  - 特征口径：决策时刻之前因果可见的 `Chainlink` 更新值与 `staleness`
- `market_id` 与 `condition_id` 当前仍同源同值，均来自 Polymarket 原始事件的 `market` 字段；新数据集不得擅自改变这一主键口径。
- 如果原始 Polymarket 文件缺少 `market_resolved`，必须通过 `polymarket_asset_map_overrides.json` 补齐映射，直至缺口清零。

原始文件读取约定：

- `finalized` 文件优先，必要时才回退到 `*-running.*`
- 同一源目录有多个 `.ndjson` / `.nojson` 分片时，按文件名顺序拼接
- canonical raw 原始事实层仍保留 `ndjson/csv`；如需列式压缩、统一读取路径或存储降本，应使用
  `model/parquet-data/<dataset_version>/` 下与 raw 同构的 **typed parquet 原始镜像层**，而不是手工改造出另一套自定义中间格式

补充口径（typed parquet 原始镜像层）：

- 当前仓库允许在 `model/parquet-data/<dataset_version>/` 下维护一套**typed parquet 原始镜像层**，
  作为 `ndjson/csv` 的列式镜像，而不是新的训练层表。
- parquet 镜像层的推荐布局与 raw 保持同构：

```text
model/parquet-data/<dataset_version>/
  <window_id>/
    btc-updown-5m/
      btc-updown-5m-<market_start_ts>.parquet
    btcusdt-orderbook/
      *.parquet
    btcusdt-price/
      *_ms.parquet
      *_ms.metadata.parquet
    rtds_chainlink/
      *.parquet
```

- 这套镜像层当前适用于**双轨验证与存储压缩**；在 `M0 / replay / feature` 等价性验收通过前，
  不应直接删除 `model/data-v*/` 下的 raw 文件。
- 当前已完成的**强验证样本**仍是 `data-v1`：
  - 文件覆盖：`584 -> 584`
  - 逐源行数一致
  - 单窗口 `manifest / labels / validation` 等价
  - 单窗口 `replay-engine` 报告等价
  - 单窗口 `feature-engine` 特征帧等价
- 当前已完成的**最新全量 coverage 校验**是 `data-v4`：
  - `verify_parquet_raw_coverage.py` 结果：`3016 -> 3016`
  - `missing_count=0`
  - `extra_count=0`
  - `row_mismatch_count=0`
- 上述 `data-v4` 结论当前只证明**文件覆盖与逐文件行数一致**；它不是“所有版本、全链路、全窗口都已完全等价”的同义表述。
- 如需业务关系、代码入口、命令范式与运维注意事项的一站式交接说明，参见
  `poly-arb-ai/dev-docs/Typed Parquet说明文档.md`

## 4. 训练层与跨阶段接口

### 4.1 M0 训练层产物

每个新数据集版本至少应能稳定生成：

- `manifest.parquet`
- `labels.parquet`
- `validation.parquet`
- `tables/polymarket_events.parquet`
- `tables/binance_aggtrades.parquet`
- `tables/chainlink_updates.parquet`
- `tables/binance_orderbook_index.parquet`
- `tables/binance_orderbook_summary.parquet`
- `summary.json`

当前正式口径：

- `manifest.parquet` 不直接保存 `p2b / resolution_price`
- `p2b / resolution_price / label_up` 位于 `labels.parquet`
- `manifest.parquet`、`labels.parquet`、`validation.parquet` 包含所有发现到的 market
- `tables/*.parquet` 只包含通过验证的 market

因此：

- 下游不得只消费 `manifest.parquet`
- `M1/M2/M3/M4/M5/M6` 相关流程，凡涉及 market 选择或标签，都必须联合消费 `manifest.parquet + labels.parquet`

### 4.2 M1 / M2 / M3 的数据契约

#### 回放与特征

- `ReplayEngine` 只回放 `manifest.is_valid = true` 且 `labels.label_status = valid` 的 market
- `feature-engine` 当前输出固定为 `86` 列（`M5` 扩展后的新 schema）：
  `7 索引 + 36 Polymarket + 20 Binance + 3 BLB + 4 Chainlink + 8 Agent + 5 Long-term signal + 3 标签`
  - 旧版 `M0`–`M4` 期间输出为 `79` 列，`M5 S1` 阶段新增 `2` 列 `agent_*`（`agent_cash / agent_nav`）和 `5` 列长期信号（`settled_pnl_last_1/3/6 / session_return / rolling_drawdown`）
- `y_ev` 必须按 `t_decision + 2 * polymarket_visible_delay_ms` 的真实盘口回填，不允许退回 `t_decision` 近似
- catch-up 帧必须使用上一事件状态快照，不能偷看未来事件

#### 监督训练

- `Phase 1` 监督训练使用 `FEATURE_COLS = 65`
- 这 `65` 维是从 `86` 列特征帧中剔除 `5` 列纯索引（`dataset_version / window_id / market_id / decision_ts_ms / cold_start`）、`8` 列 `agent_*`、`5` 列 long-term signal、`3` 列标签后得到的正式输入（保留 `time_to_expiry_ms / step_index` 作为序列位置特征）
- `M5` 监督+RL 阶段输入升级为 `76` 列：`FEATURE_COLS(65) + AGENT_STATE_COLS(6) + LONG_TERM_SIGNAL_COLS(5)`；其中 `AGENT_STATE_COLS` 只取 `up_shares / down_shares / up_value / down_value / position_value / floating_pnl`，不包括 `agent_cash / agent_nav`
- `M3` 训练或联合多数据集训练时，必须：
  - 先全局合并所有 parquet
  - 再统一做严格时间前推切分
  - 或使用冻结的 `split_info.json`
- 严禁“各 parquet 各自 `time_ordered_split()` 后再 `ConcatDataset` 拼接”，这是已经验证过的时间泄露来源

#### 上下文窗口

- `context window` 允许跨 market 向前拼接历史
- 绝不能穿越未来时间
- 若采用冻结的 canonical `split_info.json`，则不得跨 split 中未纳入的 window 回看

### 4.3 M5 诊断相关数据契约

如果未来要基于 `DATA-V4` 重做 `M5` 类诊断，必须遵守以下当前经验口径：

- `tick_stream` 的 observation 维度为 `76`
- 训练/诊断默认使用 `tick_stream/*_reward_minimal.parquet`
- 旧的 `reward_clip=Some(1.0)` 口径只能作为历史对照，不再作为默认训练输入
- 如果直接重新采集 transition，而不是事后重建 `reward_minimal`，则必须显式关闭裁剪，例如传 `--reward-clip 0`
- `collect-transitions` 不应继续沿用“默认 argmax + 默认 clipped reward”作为无脑默认流程

当前已知关键结论：

- `reward_clip=Some(1.0)` 会把结算时的方向性信号严重裁平
- 纯 offline IQL 不是当前项目默认主线
- 若仅为了验证部署候选，优先评估 `signal_head + execution config`，而不是先扩展新的 RL 搜索树

## 5. 创建 DATA-V4 的标准流程

推荐按如下顺序执行。

### Step 1：创建原始目录

在 `model/` 下创建 `data-v4/`，并按窗口直接挂目录：

```text
model/data-v4/<window_id>/...
```

不要使用额外的日期层级。

### Step 2：同步三类连续源，补齐 aggtrades

先同步：

- `btc-updown-5m/`
- `btcusdt-orderbook/`
- `rtds_chainlink/`

再检查并回填 `btcusdt-price/`：

```bash
python3 model/backfill_binance_btcusdt_aggtrades_ms.py --dataset-version data-v4 --dry-run
python3 model/backfill_binance_btcusdt_aggtrades_ms.py --dataset-version data-v4
```

说明：

- `backfill_binance_btcusdt_aggtrades_ms.py` 支持任意 `data-v*`，默认值虽然还是 `data-v3`，但显式传 `--dataset-version data-v4` 即可
- 长任务必须保留进度输出，不要静默运行

### Step 3：扫描 `market_resolved` 缺口

当前脚本 `sync_polymarket_asset_map_overrides.py` 的默认扫描列表仍是 `data-v1 data-v2 data-v3`，所以对 `DATA-V4` 必须显式传 `--datasets data-v4`：

```bash
python3 model/sync_polymarket_asset_map_overrides.py \
  --datasets data-v4 \
  --report-path /tmp/data_v4_asset_map_report.json \
  --template-path /tmp/data_v4_asset_map_template.json
```

如需在线补齐：

```bash
python3 model/sync_polymarket_asset_map_overrides.py \
  --datasets data-v4 \
  --fetch-missing-from-gamma \
  --gamma-output-path /tmp/data_v4_asset_map_gamma.json \
  --report-path /tmp/data_v4_asset_map_report_after_gamma.json \
  --fail-on-missing
```

### Step 4：M0 校验与导出

```bash
python3 poly-arb-ai/data-pipeline/cli.py validate --dataset-version data-v4
python3 poly-arb-ai/data-pipeline/cli.py export --dataset-version data-v4
```

最低要求：

- 有清晰的通过/丢弃统计
- `drop_reason` 可追溯
- `summary.json` 与 `all-datasets-summary.json` 被刷新

### Step 5：回放与特征烟雾验证

回放 smoke：

```bash
cargo run --release --manifest-path poly-arb-ai/rust/Cargo.toml -p replay-engine -- \
  --dataset-version data-v4 --limit-markets 3
```

特征导出：

```bash
cargo run --release --manifest-path poly-arb-ai/rust/Cargo.toml -p feature-engine -- \
  --dataset-version data-v4 --step-ms 250 --top-k 5 \
  --output-path poly-arb-ai/rust/feature-engine/out/data-v4/features_250ms_all.parquet
```

### Step 6：监督训练与评估

如果 `DATA-V4` 要参与监督训练：

- 单独训练时，可只传 `data-v4` 的 parquet
- 联合训练时，必须和旧版本一起全局合并后统一切分

示例：

```bash
PYTHONPATH=poly-arb-ai python3 poly-arb-ai/training/train.py \
  --parquet-paths \
    poly-arb-ai/rust/feature-engine/out/data-v1/features_250ms_all.parquet \
    poly-arb-ai/rust/feature-engine/out/data-v2/features_250ms_all.parquet \
    poly-arb-ai/rust/feature-engine/out/data-v3/features_250ms_all.parquet \
    poly-arb-ai/rust/feature-engine/out/data-v4/features_250ms_all.parquet \
  --epochs 30 --batch-size 2048 --seq-len 240 \
  --output-dir /tmp/m3_v4 \
  --device cuda --amp --compile
```

### Step 7：如果要做 M5 类 transition 采集

当前推荐口径不是继续使用旧的 clipped reward 默认值。至少应满足以下之一：

- 采集时显式关闭裁剪：`--reward-clip 0`
- 采集后重建 `reward_minimal`

并且不要继续使用“纯 argmax、无探索”的退化采集方式。当前仓库已支持：

- `--collection-policy mix / mix-as`
- `--sampling-temperature`
- `--epsilon-random`

如果只是为了验证当前可部署候选，不应先扩展新的 RL 采集，而应优先跑 `signal + 0.58 + limit` 的 replay / evaluate。

## 6. DATA-V4 验收清单

`DATA-V4` 至少应满足以下检查项：

- `model/data-v4/` 下直接是 `<window_id>`，没有额外日期层
- `validate` 能完成，且 `manifest/labels/validation` 产物齐全
- `manifest.parquet + labels.parquet` 主键一致，可联合消费
- 若已生成 `model/parquet-data/data-v4/`，`verify_parquet_raw_coverage.py` 应通过；当前本地结果为
  `3016 -> 3016`，且 `missing/extra/row_mismatch` 全为 `0`
- `market_resolved` 缺口已通过覆盖表补齐到 `0`
- `replay-engine` 能对样本窗口正常回放
- `feature-engine` 能生成 `86` 列特征帧（`M5` 扩展后新 schema；旧版 `79` 列已废弃）
- 监督训练若联合多版本数据，采用的是全局时间前推切分，而不是各文件各切各的
- 若生成 transition 数据，默认使用 `reward_minimal` 或显式关闭 `reward_clip`
- 文档同步完成：`依赖环境说明.md`、`prd.md`、`技术构思v2.md`、`开发计划.md`

## 7. 明确禁止的旧口径

以下做法在当前项目状态下应视为过时或错误：

- 使用 `model/data-v4/<date>/<window_id>/...` 作为正式目录结构
- 只读取 `manifest.parquet` 而不关联 `labels.parquet`
- 用 `t_decision` 盘口近似 `y_ev`
- 多个 parquet 各自切分 train/val/test 后再拼接训练
- 把 `reward_clip=Some(1.0)` 的旧 `tick_stream` 当作默认 RL 输入
- 把“纯 offline IQL 应该会自然收敛出最终可交易 6-class policy”当作当前既定事实
